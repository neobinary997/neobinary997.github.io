# Agent 的 Reducer 模式状态注入

> 本文是《[淘宝主播 Agent 的 Harness 工程实战](./2026-08-07-淘宝主播Agent的Harness工程实战)》解读的专题深挖，聚焦上下文工程里最值得单拎出来讲的一个设计：**Reducer 模式状态注入**。

## 一、先看痛点：传统做法为什么不行

传统 Agent 的典型链路是：LLM 决策 → 调用工具 → 工具返回**完整 JSON** → 把这坨 JSON 直接 append 到聊天历史 → 下一轮 LLM 自己从一长串历史里「读懂」当前是什么状态。

在直播间这种多话题交织、几十轮对话的场景下，它撞上三堵墙：

- **状态模糊**：LLM 要从 20 轮历史里自己推断「现在讲的是哪个商品、价格改成了多少、库存还剩多少」。模型本质是概率的，推断越多越容易错。
- **上下文膨胀**：每次工具返回的完整 JSON（可能几百行 SKU、价格、库存）都进历史，Token 快速耗尽，延迟和成本失控。
- **不可回放**：状态散落在历史里、从未被显式快照过，出了问题无法精确复现「第 N 步时状态到底是什么」。

传统做法用 Python 写出来，问题一目了然：

```python
def traditional_bad_approach(history: list, tool_result_json: str) -> list:
    # 把整坨工具返回 JSON 直接塞进历史，下一轮 LLM 自己从 20 轮历史里推断状态
    history.append({"role": "tool", "content": tool_result_json})
    return history  # 历史越来越长、状态越来越模糊、无法精确回放
```

## 二、Reducer 是什么：借鉴前端 Redux 的纯函数

「Reducer」是前端状态管理库（Redux / useReducer）的核心概念：一个**纯函数** `(state, action) => newState`，接收当前状态和一个动作，返回新状态。它有三个关键性质——**纯函数、确定性、状态集中**——正好对应 LLM Agent 最缺的东西。

主播 Agent 把这个前端思想搬进了 Agent 的上下文工程，核心一句话：**LLM 只负责决策（产出 Action），Reducer 函数负责状态变更（纯函数、确定性）。**

| | 传统做法 | Reducer 模式 |
|---|---|---|
| 谁改状态 | LLM 直接在历史里产生新状态 | LLM 产出 Action，Reducer 纯函数执行变更 |
| 状态形态 | 隐式，散落在历史 JSON 里 | 显式，单一结构化 State |
| 每轮输入 | 全量历史 + 上一轮工具 JSON | 干净的最新 State 快照 |
| 确定性 | 概率性 | 确定性（同 state + action 永远产出同新 state） |

## 三、在 Agent 里怎么落地：职责分离

把「推理」和「状态变更」从耦合变成解耦，工程上分四块：State 快照、Action 意图、Reducer 纯函数、幂等去重。

```python
from dataclasses import dataclass, field, replace
from typing import Literal
import uuid

# ① State：直播间的结构化状态快照（显式、单一、可序列化）
@dataclass
class LiveState:
    session_id: str
    current_sku: str = ""
    current_price: float = 0.0
    current_stock: int = 0
    live_goal: str = ""           # 本场目标，如「清库存」
    scenario: str = "on-live"     # pre-live / on-live / post-live
    op_log: list = field(default_factory=list)  # 只留 Action 轨迹，不囤工具 JSON

# ② Action：LLM 产出的「意图」，不是最终状态；写操作必须带幂等键
@dataclass
class Action:
    type: Literal["CHANGE_PRICE", "SWITCH_PRODUCT", "SET_GOAL", "NOOP"]
    payload: dict
    idempotency_key: str = field(default_factory=lambda: str(uuid.uuid4()))

# ③ Reducer：纯函数，确定性更新 State —— 可测、可审、可回放
def reducer(state: LiveState, action: Action) -> LiveState:
    if action.type == "CHANGE_PRICE":
        return replace(state, current_sku=action.payload["sku"],
                       current_price=action.payload["price"])
    if action.type == "SWITCH_PRODUCT":
        return replace(state, current_sku=action.payload["sku"],
                       current_stock=action.payload.get("stock", state.current_stock))
    if action.type == "SET_GOAL":
        return replace(state, live_goal=action.payload["goal"])
    # 未知 Action 不改任何东西 —— 天然防越界、防幻觉
    return state

# ④ 幂等去重：框架层在 Reducer 之前做，杜绝「双改价」「双切品」
_seen_keys: set[str] = set()
def dedupe(action: Action) -> bool:
    if action.idempotency_key in _seen_keys:
        return False           # 重复指令，安全吞掉
    _seen_keys.add(action.idempotency_key)
    return True
```

关键点：Reducer 对未知 Action 默认 `return state`（不改任何东西）。这意味着模型哪怕胡乱产出一个 Action，状态也不会被污染——再配合工具调用的 Schema 强约束 + 幂等键，形成「模型说了不算，工程说了算」的双重保险。

## 四、注入方式：system-hint 替代冗长历史

这是落地的关键一环。每轮对话开始前，框架层把最新的结构化 State 序列化成一段**紧凑的 system-hint**，注入到系统提示位置，**替代**原来那堆冗长的历史工具 JSON。

于是模型每一轮看到的不是「20 轮流水账里藏着当前价格」，而是一份干净、确定、最新的状态快照——「当前 SKU、当前价格、当前库存、本场目标」一目了然。历史里只保留对话本身和 Action 轨迹，不再囤积大块工具返回体。

```python
# ⑤ system-hint 注入：把最新 State 序列化成紧凑提示，替代冗长历史
def serialize_to_hint(state: LiveState) -> str:
    return (f"【当前状态】商品SKU: {state.current_sku} | "
            f"价格: {state.current_price} | 库存: {state.current_stock} | "
            f"本场目标: {state.live_goal} | 场景: {state.scenario}")

def build_system_prompt(state: LiveState) -> str:
    return (
        "你是淘宝直播间的助理 Agent。请基于【当前状态】决策，"
        "只输出一个 Action（type + payload），不要直接修改状态。\n"
        + serialize_to_hint(state)
    )
```

## 五、一轮完整执行循环

把前面的零件串起来，一轮对话在 Harness 框架里的完整流程如下。注意每个 Hook 的插桩时机——这正是「不改写推理循环、在关键时机插入强规则」的落地。

```python
# ⑥ 一轮完整执行循环：Hook 插桩 + LLM 产 Action + Reducer 更新 State
def run_turn(state: LiveState, user_msg: str, llm, tool_runner) -> LiveState:
    # PreReasoning Hook：注入最新 State（system-hint）
    system_prompt = build_system_prompt(state)

    # LLM 只产 Action（意图），不是最终状态
    raw = llm.chat(system=system_prompt, user=user_msg)
    action = parse_action(raw)            # 结构化解析 + JSON Schema 校验

    # PreToolCall Hook：幂等去重 + 风险审批
    if not dedupe(action):
        return state                      # 重复指令，安全吞掉

    # 工具执行（带副作用，如改价）—— 由工程执行，非模型直接改
    tool_runner.run(action)

    # PostToolCall Hook：Reducer 纯函数更新 State
    new_state = reducer(state, action)
    new_state.op_log.append({"action": action.type, "key": action.idempotency_key})
    return new_state
```

一轮跑下来，状态从 `state_old` 确定性地变成 `state_new`，且 `op_log` 里留下完整 Action 轨迹——任何一步都能精确复现，也为前面的记忆对账、信任度演化提供了干净的状态基线。

## 六、为什么这套设计性价比极高

1. **把确定性从模型手里拿回工程手里**。状态变更是高风险操作（改价、切品），交给纯函数意味着同一输入永远得到同一输出，可测、可审、可回放——这恰是直播间「不可撤回」场景最需要的。
2. **降 Token + 降延迟**。不再把完整 JSON 堆进历史，上下文体积大幅收缩，既省钱又减延迟，还顺手缓解了注意力漂移（关键信息不再被淹没）。
3. **天然防幻觉 / 防越界**。Reducer 对未知 Action 默认不改状态，模型胡乱产出 Action 也不会污染状态；再配合 Schema 强约束 + 幂等键，形成双重保险。
4. **可回放可对账**。State 是显式快照，任何一步都能精确复现，也为记忆对账、信任度演化提供干净的状态基线。

一句话总结它的精髓：**让 LLM 做 LLM 擅长的事（理解意图、产出 Action），让工程代码做工程擅长的事（确定性状态机）**——这正是 Harness「水流理论」里「河道修好，水流有波动整体也可控」的一个最佳注脚。它不是某个高深算法，而是一个边界划得极干净的工程取舍，也因此是当前 Agent 上下文工程里**最容易迁移、性价比最高**的设计之一，不限于直播，凡 Agent 会反复操作结构化状态的场景都能套用。

## 七、小结

Reducer 模式状态注入本质做了一件很简单但极重要的事：**把状态从「模型隐式推断」变成「工程显式管理」**。

- LLM 只产 Action（决策）；
- Reducer 纯函数管 State 变更（确定性）；
- system-hint 每轮注入最新快照（干净、省 Token）；
- 幂等键 + Schema 在前兜底（防重放、防越界）。

模型会一代代变强，但包裹模型的这层工程骨架，才是把「能用的 Demo」变成「敢上线的产品」的真正壁垒。
