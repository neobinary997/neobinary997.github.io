# 淘宝主播 Agent 的 Harness 工程实战（总结梳理）

> **原文来源**：微信公众号「大淘宝技术」
> **作者**：澄沨（淘天集团-直播技术团队）
> **发布时间**：2026-08-07
> **原文链接**：https://mp.weixin.qq.com/s/Ky7oM7NIytxThVk4APjiTg
> **一句话概括**：在直播间这种「高风险、高并发、不可撤回、主播无暇复核」的极端场景下，用模型外层的工程化骨架（Harness）把「概率性、易漂移、偶尔失控」的大模型能力，变成可用、可控、可演化的工业级产品。

---

## 一、为什么主播 Agent 需要 Harness？

**核心主张**：模型能力是概率的、会漂移的、偶尔失控的；真正让 Agent 可用、可控、可演化的，是模型外面那层工程化的「骨架」——结构化的上下文、约束性的工具协议、生命周期的钩子、可恢复的状态、可观测的评估。

**为什么不能用「个人助手」的实践直接套用**：OpenClaw / Claude Code / Hermes 等公开的 Harness 实践验证场景都是「个人助手」形态——单用户、本机运行、出错自己看日志重跑，延迟和成本都不敏感。而淘宝主播 Agent 把 Harness 工程推到了极端苛刻的压力测试场：

1. **操作即时生效且面向公众**：Agent 指令一旦下发，错误无法撤回，代价是真金白银。
2. **主播注意力极度稀缺**：主播在镜头前要讲解、互动、看数据，无余力逐条核验 Agent 动作 → 安全边界必须由工程兜底，而非人工复核。
3. **多话题高频交织**：播前准备、中控指令、商品操作交替出现，单轮对话可能同时涉及选品、组货、排序、控场，上下文极易污染和漂移。
4. **长程、可中断、要恢复**：直播动辄数小时，跨设备跨端切换是常态，会话中断后必须精确续连，不能让 Agent「失忆」。

## 二、Harness 建设思想

### 2.1 Harness 的形式化定义：六元组

**H = (E, T, C, S, L, V)**

| 元素 | 全称 | 职责 |
|------|------|------|
| E | Execution Loop | 执行循环 |
| T | Tool Registry | 工具注册 |
| C | Context Management | 上下文管理 |
| S | State Storage | 状态存储 |
| L | Lifecycle Hooks | 生命周期钩子 |
| V | Evaluation Interface | 评估接口 |

**价值**：把「Agent 工程」从零散的 Prompt 技巧和 if-else，升级为有明确分工的系统架构。任何 Agent 项目都可以拿这六个维度对照自查缺口。

**辅助视角「水流理论」**：人控制方向、设定边界与检查点，AI 在边界内自主推进；工程师建设的是「河道、闸门、护栏」（即 Harness）。模型再强，没有河道会泛滥成灾；河道修好，水流有波动整体也可控。

### 2.2 分层结构：业务方写 Skill，框架层兜底脏活

**核心思想**：业务方专注写 Skill，框架层兜住所有安全、状态、上下文与可观测的脏活。

- **责任边界划干净**：把「会变的」和「不变的」彻底拆分。框架层提供执行循环、上下文治理、安全防护、状态持久化、审计观测等「不变的工程能力」；业务方只需声明「技能能干什么、风险等级多高、参数怎么校验」，其余全部由框架兜底。
- **安全是纵深防御而非单点**：任何单一防护层都可能被绕过，故建立从 Prompt 边界到执行审计的五层防御。
- **长程任务「可恢复、可观测、可干预」**：三层 Checkpoint 机制保证任意时刻中断可精确续连；DAG 全局规划替代 ReAct 单步局部决策。

### 2.3 工程载体：逻辑统一工作区，物理分而治之

业界 Harness Framework 喜欢用「文件系统 Workspace」作为唯一事实来源（单机/个人助手形态下优雅），但主播 Agent 需服务海量主播、多副本水平扩容、高并发实时读写，单文件系统假设不成立。**取舍**：逻辑视图上仍向 Agent 暴露统一「工作区」抽象，物理落地上按三类资产的读写特征分选存储后端，框架层把异构存储拼装成对 Agent 透明的整体。

| 资产 | 存储 | 理由 |
|------|------|------|
| 记忆 | Hologres | 数据模型「向量 + 全文 + 标量」三位一体（原文全文检索 + 向量语义检索 + JSONB 元数据精确过滤），支撑混合检索 |
| 技能 | GitLab | Skill 是带 Schema 约束、能力域声明、校验规则的代码资产，天然适合 Git 维护；上线前走预检平台 + Code Review + 灰度发布 |
| 会话 | MySQL | 对一致性与点查性能要求最高，agent_session 表以 user_id + session_id + state_key 为索引按需点查加载，状态落共享存储而非副本本地内存，才能多副本对等部署、跨节点一致、服务不中断 |

**收益**：① 检索密集的走 Holo、版本化的走 GitLab、强一致的走 MySQL，不用一套存储硬扛所有负载；② 业务逻辑只面向「加载上下文、读写记忆、调用技能、持久化状态」等语义接口，不感知底层存储，存储演进不反向冲击业务代码。

## 三、八项工程实战

### 1. 上下文工程：看得清、记得住、不漂移

要解决的两堵墙：**上下文膨胀**（Token 耗尽、延迟飙升、成本失控）和**注意力漂移**（关键信息淹没在流水账里）。

- **手段一：分层压缩，而非无脑截断**。常规超阈值走 3 层压缩（压缩历史工具调用 / 摘要历史对话轮次 / 压缩当前轮次消息）；对话超 N 轮触发 Session 级话题分段，压缩为结构化摘要并打场景标签（pre-live / on-live / post-live），支持按场景聚合检索。
- **手段二：Reducer 模式更新状态（全文最值得强调的设计）**。传统做法把每轮工具调用完整 JSON 塞进历史让 LLM 自己推断，带来三问题：**状态模糊**（要从 20 轮对话里推断「现在讲哪个商品、价格改了多少」）、**上下文膨胀**、**不可回放**。借鉴前端状态管理 Reducer 思想做职责分离：**LLM 只负责决策（产生 Action），Reducer 函数负责状态变更（纯函数、确定性）**；每轮对话前把最新结构化 State 序列化后通过 system-hint 注入，替代冗长系统提示词 → 模型每轮看到一份干净、确定、最新的状态快照。
- **手段三：大上下文卸载**。体量大但不必时刻在场的（完整商品列表、长篇历史数据、上传大文件）外存储卸载到 oss/tair（路径 id + 预览）：需提取数据时读 fileKey 沙箱执行 shell 过滤；只需摘要时摘要从工具输出返回。

### 2. 工具调用：能力边界、强约束与错误恢复

- **能力边界声明**：每个 Skill 注册时声明能力范围与限制，调用前校验请求是否落在能力域内；新 Skill 上线前过预检平台验证定位声明 → 从源头避免「越权调用」。
- **Schema 强约束 + 幂等设计**：所有工具签名和决策输出用 JSON Schema 约束，结构层面杜绝非法参数；**所有有副作用的写操作（改价、切品、发券）必须携带幂等键（UUID）**，框架层执行前做去重校验 → 即使网络重试或重新规划导致同一指令发两次，也绝不出现「双切品」「双改价」。
- **结构化错误码 + 自动修复**：工具执行返回结构化错误码体系，框架按错误类别采取不同恢复策略。

### 3. 生命周期 Hook：关键时机插入强规则

哲学：**不改写模型推理循环，而是在循环关键时机插入钩子做拦截、注入、记录**，保留自主推理灵活性的同时施加确定性工程约束。

| Hook | 时机 | 作用 |
|------|------|------|
| PreReasoning | 推理前 | 注入最新 State、按 query 预加载记忆 |
| PreToolCall | 调用工具前 | 安全拦截：校验能力边界、幂等键、风险等级审批 |
| PostToolCall | 工具调用后 | 结果校验与状态更新：对照实时业务数据交叉验证，触发 Reducer 更新 State |
| PostReasoning | 推理后 | 幻觉检测：验证输出与真实数据一致、是否正确调用工具 |
| OnSessionEnd / OnLiveEnd | 会话/直播结束 | 记忆回写：提炼场景轨迹事件写入记忆文件，触发后台整合 |

好处：把「安全、可观测、持续演化」等横切关注点从业务逻辑彻底解耦，统一收敛到框架层。

### 4. 沙箱执行防护：不可信代码在隔离边界内运行

只要 Agent 会执行 Shell、跑用户/模型提供的代码或第三方 Skill 脚本，这些输入就必须当作不可信对待。框架层为所有代码类执行统一套沙箱：

- **身份与文件系统**：非特权用户运行、根文件系统只读；
- **资源配额**：CPU ≤ 50%、进程数上限 ≤ 64，掐死资源耗尽型攻击；
- **网络**：默认禁止出站连接，仅最小化 allowlist 放行；
- **系统调用**：白名单收敛、禁用高危调用；
- **环境隔离**：绝不注入宿主机环境变量。

配套约束：工具层强制 timeout 上限（Agent 传入的 timeout 只能缩小不能放大）；stdout/stderr 上限 64KB 超出截断；system prompt 声明「沙箱输出不可信」；所有执行记录（代码 + 输出 + user_id + session_id）完整写审计日志。

### 5. 五层安全防护体系：纵深防御

| 层 | 机制 | 拦什么 |
|----|------|--------|
| 第一层 | Prompt 边界硬编码 + Skill 定位声明 + Skill 预校验 | 能力越界 |
| 第二层 | Schema 强约束 + 幂等设计 | 非法参数、重复执行 |
| 第三层 | Approval 审批分层 | 高风险操作。平台级红线框架层定义，Skill 级风险业务方声明（如调价范围），配套校验规则 |
| 第四层 | 工具执行验证层（业务方控制） | 执行时的业务规则校验，返回结构化错误码 + 自动修复 |
| 第五层 | 执行审计记录 | 全生命周期记录：实时监控告警 / 事后复盘回放 / 模型优化数据 / 争议处理的不可篡改证据链 |

第三层的设计权衡很关键：直播操作不能每步都让主播确认（Agent 就没意义了），也不能全部放行（风险太高）→ 按风险等级分层审批，平衡安全与流畅。

### 6. 异常处理与降级策略

模型一定会出错，关键是出错时 Harness 能否优雅兜底（针对 Agent 推理层面的典型异常，设计了对应检测与降级策略）。

### 7. LLM 驱动的 PlanEngine：从 ReAct 单步到 DAG 全局规划

**背景**：主播指令常是复合的（如「生成开播提案 → 创建直播间 → 同步历史场次商品 → 生成讲解手卡 → 开启智能标题」），带先后依赖；ReAct 单步局部决策容易顾此失彼。

**目标**：从「逐步推理的局部最优」演进到「基于 DAG 的全局最优」，围绕五个目标建设：

- **可恢复**：三层 Checkpoint（每轮对话后持久化状态 / 每个子任务完成后写入 / 计划变更时保存完整快照），恢复时状态归一、断点续连，计划变更支持人工干预确认。
- **可观测**：子任务独立 TraceID 全链路追踪；Plan / SubTask / Tool Call 三级状态实时可视化。
- **提升执行效率**：DAG 中无依赖的子任务并行调度。
- **提升执行成功率**：固定规则 + 语义双重 Schema 校验；失败子任务自动重试；**增量 Replan**（子任务失败只重规划受影响的后续节点，不推倒重来）；Token 额度控制防资源耗尽。
- **降低上下文漂移**：执行进度外挂（不占 Context Window）、SubAgent 上下文隔离、Plan 快照持久化（压缩前落盘）、System-Hint 动态注入。

planner 还可基于小模型 SFT 微调 + 强化学习，提升主播垂直领域效率与准确性。**实测对比**（平均 7 步复杂任务，基模 qwen3.7-max）：PlanEngine 在执行效率（工具执行冗余率、迭代轮次）和准确率（执行成功率、子任务覆盖率）上均优于原生 ReAct。

### 8. 评测体系：质量可量化、可追踪

- **trace 分析**：接入 Langfuse 可视化 trace。
- **离线评测**：构建播前/播中/播后各场景标注数据集；**特别加入对抗样本**（极端改价、违规诱导、模糊指令等边界 Case），专门验证五层防护是否有效。
- **在线评测**：实时指标看板——操作成功率（工具调用成功数/总调用数）、审批通过率（soft-gate/hard-gate 通过率，过低说明决策质量下降）、主播干预率（主播主动纠正 Agent 的频率，直接反映自主决策可靠度）、端到端延迟。
- **主播满意度**：每场直播结束主播打分（1–5 分），会话级主观质量信号。

## 四、Harness 记忆体系：越用越懂主播

记忆体系被 Harness 工程思想深度重塑，与上下文管理（C）、状态存储（S）、Hook（L）、评估（V）紧密咬合。

### 4.1 三层记忆模型（按「信任来源」分层）

- **L1 会话记忆（Session Memory）**：反映主播的主观行为和声明。
- **L2 事实记忆（Fact Memory）**：对 L1 做客观信息补充。
- **L3 行为记忆（Behavior Memory）**：对 L1 做信任度评分。

冷启动时基于 L2、L3 历史数据给主播推荐方案；随使用基于交互反馈不断进化。

### 4.2 记忆对账与信任度进化（灵魂设计）

**出发点**：主播「说的」和「做的」不一定一致（嘴上说开场上引流款，L3 显示近 3 场实际都上氛围款且效果不错）。通用记忆系统遇到矛盾，要么新信息覆盖旧信息，要么干脆忽略。

**做法**：引入**记忆对账机制**——**矛盾时不粗暴覆盖，而是累积证据、达到阈值后由 Agent 主动和主播确认**。既尊重主播主观意图（L1 第一优先级），又让记忆基于客观事实持续进化，避免「AI 自作主张改了我的设定」这种破坏信任的体验。

**支撑**：标准化 **Decision Trace Log**（每条 trace 记录「问什么 / Agent 答什么 / 主播选什么 / 最终效果」），本质是把评估接口（V）的可观测数据反向喂给记忆系统做自进化 → 更新 **trust_score**（信任度）→ trust_score 反向决定输出形态：**信任度高大胆给建议，信任度低只摆数据不下结论**。

> 这一闭环把「Agent 与主播的信任关系」从模糊感觉变成可度量、可演化、可解释的工程量。

### 4.3 直播场景多因子遗忘

比通用的「时间衰减」更精细，采用**多因子加权衰减**：

- **直播场景相关性**：品类集中度、常播品类策略等；
- **信息新鲜度分级**：偏好、话术模板等经验型记忆慢衰减；价格、平台规则等波动型记忆快衰减；
- **时间衰减**：常规时间维度；
- **可信度因子**：经验证/高使用频率的记忆获得加成；被证伪的记忆急剧降权；未验证的保持基础衰减。

配套：定时清理策略（采纳/召回次数 ≤ 阈值清理、超期清理）+ 记忆冲突处理（Last-Write-Wins + 自定义优先级，或召回时把冲突呈现给 Agent 主动确认），保证记忆库长期不失控、不腐坏。

## 五、总结与启示

文章始终在回答一个问题：**当模型能力是不确定的，怎么把它工程化成一个在高风险直播场景里可用、可控、可演化的系统？**

答案就是 Harness 这层骨架：
- 用 **H = (E, T, C, S, L, V) 六元组**划清工程边界；
- 用「**业务方写 Skill、框架兜底脏活**」的分层把迭代效率和工程质量解耦；
- 用上下文工程、强约束工具调用、生命周期 Hook 搭好通用底座；
- 用五层纵深防御、DAG 全局规划、离在线评测扛住直播场景的极端要求；
- 用被 Harness 重塑的记忆体系（三层记忆、记忆对账、信任度自进化、多因子遗忘）让 Agent「越用越懂主播」。

**金句**：模型会一代代变强，但包裹模型的这层 Harness 工程，才是把「能用的 Demo」变成「敢上线的产品」的真正壁垒。

## 六、延伸思考（个人整理）

1. **通用可迁移性**：六元组、Reducer 状态注入、幂等键、五层纵深防御、Hook 插桩这套方法论，不限于直播——凡是 Agent 会执行有副作用的外部操作（支付、下单、发布、控制设备）的高风险场景都可复用。
2. **「LLM 只决策、Reducer 管状态」是亮点**：把确定性从模型手里拿回工程手里，既降 Token 成本又大幅提正确率，是当前 Agent 上下文工程里性价比最高的设计之一。
3. **记忆对账 + 信任度演化**：把「信任」做成可度量、可更新的工程量，解决了 LLM 产品长期使用的核心痛点（AI 擅自改设定 → 用户失去信任）。
4. **业务与框架解耦的代价**：需要较强的框架抽象能力与预检/灰度体系支撑（GitLab 技能发布流程），小团队直接照搬成本较高，可先落地方案中的上下文工程、幂等、Hook 三件套。
