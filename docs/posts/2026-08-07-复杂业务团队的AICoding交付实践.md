# 复杂业务团队的 AI Coding 交付实践（解读）

> **原文来源**：微信公众号「大淘宝技术」
> **作者**：寂秋（淘天集团-物流技术团队）
> **发布时间**：2026-08-05
> **原文链接**：https://mp.weixin.qq.com/s/aopO-3KO9lenKF5WHhBD7w
> **一句话概括**：复杂业务团队不能指望"模型升级就能全自动交付"，先把团队自己的知识库、研发协议（RD 流程）和质量门禁沉淀好，AI 才能从单点提效变成可交付、可控、可演进的研发系统。
> **业务场景**：物流订单履约后端（多业务域、多应用、多模块、历史包袱重）——本文解读时将其作为案例，提炼可迁移的通用设计思路。

---

## 一、核心主张与通用问题

**通用问题**：当团队业务复杂度高（多域、多应用、大量历史妥协）、AI Coding 工具已经能跑起来时，为什么"代码采纳率"上不去、交付还是要靠人救火？怎么让 AI 真正进入生产交付链路而不是停留在 demo 和辅助？

**核心主张（三层）**：

1. **工具可以换、模型可以升级，但团队自己的业务上下文、研发协议和质量门禁必须自己沉淀**——这是 AI 交付的"资产底座"，也是与工具解耦后依然可迁移的部分。
2. **不追求"短时间全自动化"**：自动化跑得越快，对底座要求越高；知识库不准、requirement 不清、review 点没设计好时，自动化只会把错误更快执行完。**先打底，再自动化**。
3. **交付目标不是"代码 100% AI 生成"的纯度**，而是总交付成本更低、质量更稳、风险更可控。做到 95% 后手改更快就手改。

**原文场景关键约束 → 通用问题映射**：

| 物流团队的具体约束 | 抽象后的通用问题 |
|--------------------|------------------|
| 多业务域、多应用、多模块 | 复杂业务团队如何让 AI 在庞大代码库中定位正确上下文 |
| 大量架构妥协、历史包袱 | 历史兼容逻辑、扩展点如何不靠口头传承而结构化沉淀 |
| 需求跨多应用、异步链路长 | 跨应用需求如何拆解、接续、对账，避免"开发中断上下文丢失" |
| 出错的返工成本极高 | 如何把错误拦截在早期阶段（fail-fast），而非联调/上线时才发现 |
| 团队每个人 AI 用法不统一 | 如何把个人经验沉淀为团队可复用的研发协议 |

## 二、可迁移的通用设计思路（核心产出）

### 思路 1：知识库分层治理——"稳定上下文"与"实现事实"分离

- **通用问题**：AI 需要团队业务上下文，但"全量喂给模型"不现实（上下文窗口、可信度），"没有知识"和"错误知识"哪个更危险？
- **通用解法**：把知识按**稳定程度和归属范围**分层存放，AI 按需渐进式加载，而不是一次全读。核心原则：
  - **KB 提供稳定上下文，当前代码仍然是实现事实**——接口签名、字段、Topic 等易变内容在 KB 里只做"定位入口"，改代码前必须回到仓库核对；
  - **错误知识比没有知识更危险**——没有知识时 AI 至少会暴露不确定，错误知识被当成事实会直接把实现带偏；
  - **知识流转有生命周期**：personal（个人经验）→ candidate（候选暂存）→ owner review → official（正式）→ 引用/更新/deprecated。
- **原文实现**：`knowledge/` 下分 `main`（跨应用通用）/ `applications`（应用级，内部再分 product/solution/base/tech）/ `candidate`（候选暂存区）/ `personal` / `template`；用 ROUTING 索引渐进式加载。
- **适用场景与边界**：适合知识量大、多团队共享、AI 深度介入编码的团队。**边界**：小团队/单人项目可大幅简化（两层即可）；依赖团队愿意持续维护 KB，否则 KB 会腐烂成"错误知识源头"。

### 思路 2：研发流程文件化——用 Markdown + YAML 承载研发状态

- **通用问题**：Coding Agent 的会话是易失的、聊天式的，如何保证"开发可以中断、研发上下文不丢"？如何让流程不绑定某一款 Agent 工具？
- **通用解法**：把研发过程中的关键状态全部落盘为**可读、可 diff、可 review 的文件**（Markdown + YAML），会话只负责执行，文件才是事实来源。新会话通过读取这些文件即可无缝接续。
  - **不绑定具体 Coding Agent**：只要 Agent 能读写这套文件协议，就能接入同一套研发流程——工具可替换，协议是资产；
  - **原始需求不能直接进编码**：先验证 PRD 缺口，再产出"应用级开发契约"（requirement.md），契约确认后才动手。
- **原文实现**：`rd/requirements/{requirementId}/` 下按阶段落盘：clarification.md、analysis.md、decomposition.yaml、requirement.md（应用级契约）、implementation-check.md（对账）、continue-prompt.md（接续提示）、status.md。
- **适用场景与边界**：适合多人协作、需求频繁交接、需要审计追溯的团队。**边界**：文件化有维护成本，追求极致轻量的个人项目不需要；流程节点不宜过重，否则工具感大于效率。

### 思路 3：质量门禁前置——fail-fast 的人机协同 review 点

- **通用问题**：AI 产出质量不稳定，错误发现得越晚返工成本越高。人不可能也没必要 review 每个字节，那人在哪里介入？
- **通用解法**：把质量检查设计成**流程中的门禁节点**，每个节点检查特定类型的问题，只把"最容易造成返工和事故的业务事实"留给人工确认：
  - **前置哲学**：能在 PRD 阶段暴露的问题不拖到 requirement，能拖到 requirement 的不拖到编码，能拖到方案阶段的不拖到联调——越晚发现，返工成本越高；
  - **人工介入点收敛**：人不在所有地方介入，只在关键业务事实上介入（校验前置/后置、状态来源、历史兼容、异步事件是否真实调用外部服务、开关默认值、发布灰度等）；
  - **质量指标不只看代码行数**：PRD 阶段发现多少 open item、requirement 拦截多少不清晰项、validate 发现多少 diff 不一致、人工中断发生在哪些阶段——用"中断位置"反推流程薄弱点。
- **原文实现**：命令链 `/rd:verify-prd → clarify → analyze → decompose → verify-requirement → apply → validate → code-review → release-plan`，每个节点对应一个门禁。
- **适用场景与边界**：适合任何"AI 产出进入生产链路"的场景。**边界**：门禁数量和位置需要按团队风险承受度调优，门禁过多会拖慢交付，过少则形同虚设。

### 思路 4：先打底再自动化——确定性优先于速度

- **通用问题**：团队刚引入 AI Coding，是先追求"全自动"还是先做基础建设？
- **通用解法**：**自动化是底座之上的加速器，不是底座本身**。第一阶段把时间花在三件事：知识库打磨、RD 流程打磨、质量门禁打磨；跑通后再逐步把流程动作交给 Agent 自动推进，最后才做完整协同交付。
- **原文实现**：三阶段落地节奏——知识库 + 工具链 → 自动化流程 → 自主协同交付（本文重点在第一阶段）。
- **适用场景与边界**：适合任何 AI 研发落地初期的团队。**边界**：若业务极简单、AI 单点提效已够用，不必强行上全套流程；越复杂的业务，越应该先打底。

### 思路 5：AI 研发 Harness——两层确定性

- **通用问题**：AI 进入真实交付后，如何让"运行环境"和"研发行为"都可预期、可控、有边界？
- **通用解法**：用 Harness（工程骨架）统一收拢知识库、工具链、权限、流程状态、质量门禁、验证规则和发布约束，提供两层确定性：
  - **运行环境的确定性**：Agent 知道本地仓库在哪、用哪些命令、先读哪些知识入口、哪些文件是权威上下文、哪些动作必须停下等人确认；
  - **研发协议的确定性**：输入先 verify → 知识按 ROUTING 加载 → 需求分阶段落盘 → 应用级 requirement 先确认 → 编码按契约执行 → validate 对账 → 发布前 review → 稳定知识回补。
  - **数据安全边界**：只让 Agent 读取当前需求需要的仓库和知识目录；敏感文档、线上数据、密钥、客户信息不进 prompt。
- **原文实现**：物流团队将上述三层资产（命令协议层/知识资产层/RD 过程资产层）统一收拢为"AI 研发 Harness"。
- **适用场景与边界**：适合 AI 深度介入生产代码的团队。**边界**：Harness 的构建成本高，小团队可先落地知识库 + 门禁两件套，不必一步到位。

## 三、原文实现细节（作为案例支撑）

### 三层资产架构

```
命令协议层    -> .agents/commands/ -> .agents/skills/
知识资产层    -> knowledge/
RD 过程资产层 -> rd/requirements/{requirementId}/
```

### 知识库目录结构（分层 + 渐进式加载）

```
knowledge/
├── main/          # 跨应用通用知识（核心术语、跨应用流程、全局状态、全局技术约束）
├── applications/  # 应用范围知识（application-xxx.md 总览 + domain/product/solution/base + tech）
├── candidate/     # 候选知识暂存区（未确认内容先进这里）
├── personal/      # 个人研发经验和踩坑记录
├── template/      # 强约束知识写作模板（YAML Front Matter：类型/状态/来源/证据/置信度/稳定性/标签/锚点）
├── INDEX.md / README.md / KNOWLEDGE-RULES.md / ROUTING.md
```

### 核心命令链（研发流程）

```
/rd:verify-prd（PRD验证）→ /rd:work（通用路由）→ /rd:clarify（澄清）
→ /rd:analyze（分析）→ /rd:decompose（拆解）→ /rd:verify-requirement（确认）
→ 应用仓库开发 → /rd:apply（实现）→ /rd:validate（对账）
→ /rd:code-review（CR）→ /rd:release-plan（发布计划）→ 发布 → 知识回补
```

### 真实案例：两轮交付对比

需求：上游服务商新回告状态触发"差异调整"，需在主流程入口前置校验 + 事件驱动异步订正。

| 维度 | 第一轮 | 第二轮 |
|------|--------|--------|
| 代码采纳率 | ~75% | 95%+ |
| 人工中断次数 | - | 3 次（澄清 1 + Review 调整 2） |
| 关键问题 | 前置校验位置放错（放在流程靠后位置） | 两阶段异步架构明确写入 requirement |
| 归因 | PRD/澄清/设计未表达关键架构约束 | 知识库 + requirement + review 点前置生效 |

**归因分析的价值**：把每一次失败归到具体层（PRD 表达不清 / 知识库缺失 / 扩展点判断错误 / 纯编码问题），让流程持续自优化。

## 四、总结与启示

这篇文章本质上是把「AI 研发交付」从"工具技巧"升级为"系统设计"的工程实践，可迁移的方法论：

1. **知识分层是 AI 交付的地基**：稳定上下文与实现事实分离，渐进式加载，错误知识防入库（candidate 暂存 + owner review）。
2. **文件化流程是 AI 交付的骨架**：研发状态落盘、契约先行、不绑定工具，保证"开发可中断、上下文不丢"。
3. **门禁前置是 AI 交付的刹车**：fail-fast 哲学 + 人工只在关键业务事实处介入，用"中断位置"反推流程薄弱点。
4. **先打底再自动化**：知识库/流程/门禁打磨好之前，自动化只会加速错误。
5. **用 Harness 收拢确定性**：运行环境与研发协议两层确定性 + 数据安全边界，是 AI 深入生产的必要条件。

## 五、延伸思考（个人整理）

1. **与上一篇文章《淘宝主播 Agent 的 Harness 工程实战》是姊妹篇**：上一篇是"Agent 面向用户的工程化"，这篇是"Agent 面向研发的工程化"——同一套 Harness 思想（确定性骨架包裹概率性模型）在两个不同场景落地，互相印证了可迁移性。
2. **"知识分层"思路可迁移到任意 AI 知识库/RAG 场景**：main（全局）/applications（域级）/candidate（暂存）/personal（个人）的分层 + ROUTING 渐进式加载 + 错误知识防入，是知识工程里性价比很高的通用设计，不止用于 Coding。
3. **"门禁前置 + 人工介入点收敛"是 AI 人机协同的通用范式**：不是"人审所有"，而是"人在关键业务事实上审"——这对任何 AI 生成内容进入生产链路的场景（代码、文案、数据、客服回复）都适用。
4. **局限与代价**：这套体系明显偏重——知识库维护、文件化流程、门禁节点都需要持续投入，小团队或单人项目直接照搬会被流程拖累；落地建议是先做"知识库 + 门禁两件套"，跑通再补 RD 流程细节。
5. **衡量标准值得借鉴**：用"人工中断发生在哪个阶段"作为流程质量指标很巧妙——它把"人被迫救火的位置"变成流程体检报告，比单纯看采纳率更能定位系统性问题。
